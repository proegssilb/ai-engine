# Spike: per-tensor placement through llama.cpp's C API, from Rust

**Question:** If we use llama.cpp as a library, can a Rust control plane decide
where each piece of a model lives, including the RAM vs SSD split that
llama.cpp's own flags can't express?

> Project context for this spike: [../../docs/vision.md](../../docs/vision.md) (what we're building) and [../../docs/decisions.md](../../docs/decisions.md) (why it's a control plane, and the boundary we'd own).

**Answer: yes, for weights.** A buffer type implemented in Rust and passed
through `llama_model_params.tensor_buft_overrides` puts the matching tensors in
memory we allocate. The tensors left on llama.cpp's default CPU buffer stay
memory-mapped from the file, so the kernel's page cache acts as the SSD tier.
Inference results are bit-identical to the unmodified baseline.

## What was run

- **llama.cpp:** pinned as a submodule (`vendor/llama.cpp` @ `a956a852c`), built
  as static CPU-only libraries by `build.rs`. Bindings are generated by bindgen
  from `llama.h`, `ggml-backend.h`, `gguf.h` and the internal
  `ggml-backend-impl.h`.
- **Model:** `scripts/make_tiny_qwen3moe.py` writes a 208 MB random-weight
  `qwen3moe` GGUF: 4 layers, 32 experts, top-4 routing, F16. Hugging Face
  wasn't reachable from the build container. The real architecture code path
  is exercised, but the text it produces is nonsense.
- **Machine:** cloud container with 4 cores, 1 NUMA node, no GPU, and AMX
  available.

```bash
git submodule update --init vendor/llama.cpp
pip install numpy
python3 spikes/placement/scripts/make_tiny_qwen3moe.py spikes/placement/models/tiny-qwen3moe.gguf
cd spikes/placement && cargo build --release          # add --features cuda for GPUs
./target/release/placement-spike models/tiny-qwen3moe.gguf --evict --pin 'blk\.[01]\.ffn_.*_exps' --numa 0
```

Placement rules are `--place REGEX=DEST`, tried in order with the first match
winning, like llama.cpp's `-ot`. `DEST` is `pinned` (the Rust buffer), `CPU`
(llama.cpp's default CPU buffer, which is the mmap'd file when
`--load-mode mmap`), or a device name such as `CUDA0`. `--pin REGEX` is short
for `--place REGEX=pinned`. Run `--help` for everything else: `--gpu-layers`,
`--tensor-split`, `--numa`, `--cuda-register`, `--moe-cache`, `--extra-bufts`,
`--repeat`, `--evict`, `--per-layer`.

Each run prints a placement table (subsystem × where it lives × % in RAM) and
a `RESULT {json}` line. Locations come from llama.cpp's own debug log
(override decisions and layer-to-device assignment) plus the Rust buffer's
records. "% in RAM" is measured with `mincore()` on each tensor's real
address.

## Running on the test box (2× V100-class GPUs)

```bash
huggingface-cli download Qwen/Qwen3-30B-A3B-GGUF Qwen3-30B-A3B-Q4_K_M.gguf --local-dir ~/models
spikes/placement/bench/test-box.sh ~/models/Qwen3-30B-A3B-Q4_K_M.gguf
spikes/placement/bench/test-box.sh ~/models/Qwen3-30B-A3B-Q4_K_M.gguf pressure   # NVMe tier, needs a cgroup memory cap
```

The script builds the spike and `llama-bench` (sm_70) from the same pinned
llama.cpp, records the hardware, runs each scenario, and writes
`results/<timestamp>/summary.md`.

**Needs a CUDA 12.x toolkit.** CUDA 13 dropped Volta, and the script refuses
to start under CUDA 13 while targeting sm_70.

| scenario | what it answers |
|---|---|
| `ref` | llama-bench numbers for all-GPU and `-ot exps=CPU`: the bar to meet |
| `gpu` | Does driving llama.cpp through the C API cost anything? Should match `ref-all-gpu`. |
| `experts` | Attention on GPU, experts in host RAM held three ways: mmap, mmap + llama.cpp repacking, Rust-pinned (± `cudaHostRegister`). Shows what bypassing repacking costs, and whether pinned DMA helps prefill. |
| `mixed` | Half the experts on GPU, half in RAM: the layout from the UI mockup |
| `moecache` | llama.cpp's own GPU expert cache over each CPU-side tier |
| `pressure` | Process capped at `MEMCAP` (10G) so mmap'd experts stream from NVMe; compares with a third of the experts pinned |

**Status of the benchmark:** the CUDA build works unchanged (CUDA 12.4,
sm_70). The benchmark itself hasn't run in full, and it mostly measures
llama.cpp's own policies (op offload, the expert cache) rather than the cost of
honouring a placement. See the GPU results below.

## GPU results (2026-11-15)

Machine: Debian 13 VM, 2× Tesla PG500-216 (V100-class, 32 GB, PCIe gen3 x8 each),
Ryzen 5800X (8 vCPU), 47 GB RAM. Model: Qwen3-30B-A3B Q4_K_M (18.6 GB).

**How placement was checked.** `src/verify.rs` evaluates one prompt batch and one
token in a separate context with a scheduler eval callback. For every weight the
graph reads it records the real buffer and data address: inside the file
mapping means mmap'd, inside a Rust allocation means pinned, otherwise the
buffer's name. It also records the scheduler's run-time copies and the expert
cache's stand-in tensors. `--no-verify` skips it. The old log-derived table is
kept but shouldn't be trusted (below).

**Placement at rest (all held where noted):**

| Rules | Result |
|---|---|
| none, all layers on GPU | every weight on its layer's GPU; embeddings mmap'd |
| experts `=pinned` (all, half, or with `--cuda-register`) | all in the Rust buffer |
| attention `=pinned` | all in the Rust buffer |
| layers 0-19 experts `=CUDA1` (llama.cpp put those layers on CUDA0) | all on CUDA1 |
| experts `=CPU` with mmap | all mmap'd; **the log-derived table said `CUDA_Host`** |
| experts `=CPU`, `--load-mode none` | **`CUDA_Host`** (pinned via CUDA) unless `--no-host` |
| experts `=CPU`, `--extra-bufts --no-host` | 120 of 144 **copied into `CPU_REPACK`** |

**At run time:**
- **Op offload:** on batches of 32+ tokens, the experts each batch selects are
  copied from host RAM to GPU 0 for every batch (about 9 GB for 64 tokens, 12 GB
  for 512), through about 140 MiB of scratch reserved at startup. `--no-op-offload`
  stops it: 91 vs. 37 tok/s on 64-token prompts, 161 vs. 203 tok/s on 512.
- **Expert cache** (`--moe-cache`): on batches of up to 32 tokens the graph reads
  the cache instead of the placed experts; misses are copied from the placed
  tensors.
- **Any `--place` rule disables pipeline parallelism.** No difference measured on
  single-sequence runs (970 vs. 972 tok/s prefill, all on GPU).

**Pinned vs. pageable host memory** (experts in RAM, 3 runs each):

| Host memory | Prefill 512 | Prefill 2048 | Decode |
|---|---|---|---|
| Rust buffer, not registered | 196 tok/s | 275 tok/s | 13.5–13.7 |
| plain CPU buffer | 197 | 275 | 13.5 |
| Rust buffer + `cudaHostRegister` | 203 | 283 | 13.7–14.0 |
| llama.cpp `CUDA_Host` | 203 | 282 | 13.8–14.0 |

All on GPU for comparison: about 1000 tok/s prefill and 113–129 tok/s decode on
short runs.

**Known flaws in `verify.rs`** (from an independent review): copy volume counts
whole tensors instead of the selected experts, expert-cache counts include its
backing tensors, and weights only read through a scheduler copy show as copies
rather than as the weight (the 48 "unread" `attn_q_norm` tensors).

## CPU results (tiny model)

Pins: `blk\.[01]\.ffn_.*_exps` (routed experts of layers 0–1), `--numa 0`.
"In RAM" is measured with `mincore()` on each tensor's real address, not
inferred.

| subsystem | MiB | where it lives | in RAM after `MADV_PAGEOUT` | after generating again |
|---|---:|---|---:|---:|
| experts blk.0 | 48 | Rust buffer (mlocked, mbind node 0) | **100%** | 100% |
| experts blk.1 | 48 | Rust buffer (mlocked, mbind node 0) | **100%** | 100% |
| experts blk.2 | 48 | mmap'd file | 0% | 66% |
| experts blk.3 | 48 | mmap'd file | 0% | 27% |
| attention, norms, router, embeddings, output head | 7 | mmap'd file | 0% | 100% |

- **The Rust buffer is used:** llama.cpp reports `RustPinned model buffer size = 96.00 MiB`.
  `mlock` and `mbind` both succeed, `move_pages` reports node 0 for the
  buffer's pages, and `VmLck` is 96 MiB.
- **Correctness:** the logits hash (FNV over every logit at every step) is
  identical across baseline, pinned, `--load-mode none` + pinned, and pinning
  attention/router/embeddings instead of experts. With `--extra-bufts` the hash
  changes, because AMX kernels compute slightly differently, but pinned and
  unpinned still match each other.
- **The SSD tier is real, but kernel-managed:** after eviction, only the
  experts the router actually chose get read back (27–79% per layer). That's an
  expert LRU cache you get for free, but you can't choose its contents.
- **Timing** (illustrative only; tiny model, page cache in a VM): warm 2.4–2.9
  ms/token, 12.1 ms/token after full eviction, 7.6 ms/token after eviction when
  half the experts are pinned.

## What this means for the design

1. **Placement is a compiler target.** The UI's "subsystem → device" layout
   compiles to a list of (regex, buffer type) pairs. GGUF tensor names
   (`token_embd`, `blk.N.attn_*`, `blk.N.ffn_gate_inp`, `blk.N.ffn_*_exps`,
   `output`) line up with the subsystem boxes.
2. **There are three tiers for weights:**
   - GPU: llama.cpp's device buffer types.
   - RAM we own: a Rust buffer type, with NUMA node, mlock and hugepages under
     our control.
   - SSD: llama.cpp's default CPU buffer with mmap, as a cache whose contents
     we don't control.
3. **No C++ was written.** All the Rust code uses the C ABI only.

## Caveats

- **`ggml-backend-impl.h` is an internal header.** Implementing a buffer type
  means depending on struct layouts that aren't a stable ABI. Pin llama.cpp,
  regenerate bindings whenever the pin moves, and keep the buffer type small.
  Here it's about 200 lines (`src/pinned.rs`).
- **Pinned tensors miss out on repacking.** llama.cpp's extra CPU buffer types
  (AMX, aarch64 repack) only apply to tensors left on the default CPU path, so
  pinned weights use the plain CPU kernels. Whether that costs speed needs
  measuring on real hardware.
- **llama.cpp silently copies some weights out of the mmap by default.** With
  extra buffer types on (the default), it moved the attention matrices into a
  6 MiB AMX buffer without being asked. The "SSD tier" is therefore only
  predictable if the control plane decides about extra buffer types
  explicitly.
- **Pinned tensors are briefly held in RAM twice.** They're copied from the
  mmap, so their file pages stay in the page cache after load (load RSS was
  about 310 MB, vs 112 MB after eviction). A production loader should drop
  those ranges with `madvise` after loading.
- **Not tested here:** GPUs (CUDA buffer types plus a Rust host tier side by
  side), the new `moe_cache_size` GPU expert cache, real Qwen weights,
  quantized types, more than one NUMA node, and KV cache placement (still
  coarse, as noted in the design discussion).
