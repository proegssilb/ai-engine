# Spike: per-tensor placement through llama.cpp's C API, from Rust

**Question:** If we use llama.cpp as a library, can a Rust control plane decide
where each piece of a model lives, including the RAM vs SSD split that
llama.cpp's own flags can't express?

**Answer: yes, for weights.** A buffer type implemented in Rust and passed
through `llama_model_params.tensor_buft_overrides` puts the matching tensors in
memory we allocate. The tensors left on llama.cpp's default CPU buffer stay
memory-mapped from the file, so the kernel's page cache acts as the SSD tier.
Inference results are bit-identical to the unmodified baseline.

## What was run

- **llama.cpp:** pinned as a submodule (`vendor/llama.cpp` @ `a956a852c`), built
  as static CPU-only libraries by `build.rs`. Bindings are generated by bindgen
  from `llama.h`, `ggml-backend.h`, `gguf.h` and the internal
  `ggml-backend-impl.h`.
- **Model:** `scripts/make_tiny_qwen3moe.py` writes a 208 MB random-weight
  `qwen3moe` GGUF: 4 layers, 32 experts, top-4 routing, F16. Hugging Face
  wasn't reachable from the build container. The real architecture code path
  is exercised, but the text it produces is nonsense.
- **Machine:** cloud container with 4 cores, 1 NUMA node, no GPU, and AMX
  available.

```bash
git submodule update --init vendor/llama.cpp
pip install numpy
python3 spikes/placement/scripts/make_tiny_qwen3moe.py spikes/placement/models/tiny-qwen3moe.gguf
cd spikes/placement && cargo build --release
./target/release/placement-spike models/tiny-qwen3moe.gguf --evict --pin 'blk\.[01]\.ffn_.*_exps' --numa 0
```

| Flag | Meaning |
|---|---|
| `--pin REGEX` | Put matching tensors in the Rust buffer (repeatable). |
| `--numa N` | `mbind` that buffer to node N. |
| `--no-mlock` | Don't lock the buffer in RAM. |
| `--load-mode mmap\|none` | How llama.cpp loads everything not pinned. |
| `--extra-bufts` | Allow llama.cpp's repacked CPU buffers (AMX etc). |
| `--evict` | `MADV_PAGEOUT` everything, then generate again. |

## Results

Pins: `blk\.[01]\.ffn_.*_exps` (routed experts of layers 0–1), `--numa 0`.
"In RAM" is measured with `mincore()` on each tensor's real address, not
inferred.

| subsystem | MiB | where it lives | in RAM after `MADV_PAGEOUT` | after generating again |
|---|---:|---|---:|---:|
| experts blk.0 | 48 | Rust buffer (mlocked, mbind node 0) | **100%** | 100% |
| experts blk.1 | 48 | Rust buffer (mlocked, mbind node 0) | **100%** | 100% |
| experts blk.2 | 48 | mmap'd file | 0% | 66% |
| experts blk.3 | 48 | mmap'd file | 0% | 27% |
| attention, norms, router, embeddings, output head | 7 | mmap'd file | 0% | 100% |

- **The Rust buffer is used:** llama.cpp reports `RustPinned model buffer size = 96.00 MiB`.
  `mlock` and `mbind` both succeed, `move_pages` reports node 0 for the
  buffer's pages, and `VmLck` is 96 MiB.
- **Correctness:** the logits hash (FNV over every logit at every step) is
  identical across baseline, pinned, `--load-mode none` + pinned, and pinning
  attention/router/embeddings instead of experts. With `--extra-bufts` the hash
  changes, because AMX kernels compute slightly differently, but pinned and
  unpinned still match each other.
- **The SSD tier is real, but kernel-managed:** after eviction, only the
  experts the router actually chose get read back (27–79% per layer). That's an
  expert LRU cache you get for free, but you can't choose its contents.
- **Timing** (illustrative only; tiny model, page cache in a VM): warm 2.4–2.9
  ms/token, 12.1 ms/token after full eviction, 7.6 ms/token after eviction when
  half the experts are pinned.

## What this means for the design

1. **Placement is a compiler target.** The UI's "subsystem → device" layout
   compiles to a list of (regex, buffer type) pairs. GGUF tensor names
   (`token_embd`, `blk.N.attn_*`, `blk.N.ffn_gate_inp`, `blk.N.ffn_*_exps`,
   `output`) line up with the subsystem boxes.
2. **There are three tiers for weights:**
   - GPU: llama.cpp's device buffer types.
   - RAM we own: a Rust buffer type, with NUMA node, mlock and hugepages under
     our control.
   - SSD: llama.cpp's default CPU buffer with mmap, as a cache whose contents
     we don't control.
3. **No C++ was written.** All the Rust code uses the C ABI only.

## Caveats

- **`ggml-backend-impl.h` is an internal header.** Implementing a buffer type
  means depending on struct layouts that aren't a stable ABI. Pin llama.cpp,
  regenerate bindings whenever the pin moves, and keep the buffer type small.
  Here it's about 200 lines (`src/pinned.rs`).
- **Pinned tensors miss out on repacking.** llama.cpp's extra CPU buffer types
  (AMX, aarch64 repack) only apply to tensors left on the default CPU path, so
  pinned weights use the plain CPU kernels. Whether that costs speed needs
  measuring on real hardware.
- **llama.cpp silently copies some weights out of the mmap by default.** With
  extra buffer types on (the default), it moved the attention matrices into a
  6 MiB AMX buffer without being asked. The "SSD tier" is therefore only
  predictable if the control plane decides about extra buffer types
  explicitly.
- **Pinned tensors are briefly held in RAM twice.** They're copied from the
  mmap, so their file pages stay in the page cache after load (load RSS was
  about 310 MB, vs 112 MB after eviction). A production loader should drop
  those ranges with `madvise` after loading.
- **Not tested here:** GPUs (CUDA buffer types plus a Rust host tier side by
  side), the new `moe_cache_size` GPU expert cache, real Qwen weights,
  quantized types, more than one NUMA node, and KV cache placement (still
  coarse, as noted in the design discussion).
